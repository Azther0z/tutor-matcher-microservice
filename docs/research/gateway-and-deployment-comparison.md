# Gateway and deployment comparison

Update after this comparison: the user selected **Traefik with native Docker Swarm discovery**, replacing Express gateway and Consul. [ADR-0029](../adr/0029-traefik-swarm-discovery.md) now governs. The dated comparison below preserves the evidence and earlier alternatives; its retained-Consul recommendations are historical, not current requirements.
Researched: **8 November 2026, Asia/Bangkok**. Official sources below were accessed on that date. This is a comparison and recommendation, not an adopted architecture change or an implementation. The four gateway candidates are **Kong, Traefik, NGINX and Caddy**.

## Gateway comparison

### Project baseline and decision criteria

At research time, the former Express gateway (`api-gateway/src/index.js`, since removed) verified JWTs locally, queried Consul for passing service instances, cached discovery for one second, fell back to fixed URLs when discovery failed, and attempted at most two targets for GET transport failures. Other methods received one attempt. It created identity headers from verified token claims. It did **not** call Auth to check current account restrictions on each protected request. The replacement's current behavior is documented in the [Traefik gateway](../../infra/gateway/README.md).

The accepted [authentication decision](../adr/0018-gateway-authentication.md) and [system design](../system-design.md#identity-permissions-and-tutor-activation) require both a valid token and current Auth account state for protected new requests. A suspended account must therefore lose access before an otherwise valid JWT expires. Every candidate needs an Auth integration; buying native JWT validation does not supply Tutor Matcher's account policy. The accepted [Consul decision](../adr/0021-consul-discovery.md) also requires health-aware discovery and an explicit degraded-routing policy.

The target keeps client-facing and gateway-to-domain operations on REST. The [20 private domain RPCs](../../contracts/grpc/README.md) use gRPC, with RabbitMQ for asynchronous work. Gateway replacement does not require putting these private RPCs on a public gateway.

“Core” means the open-source distribution, not every module listed on a vendor website. Paid editions and community extensions are separate choices.

### Health checks, retries and rate limits

| Concern | Kong | Traefik | NGINX | Caddy |
| --- | --- | --- | --- | --- |
| Health-aware routing | OSS Upstreams/Targets support active and passive checks. Consul Catalog can filter registry health. | OSS passive failure detection with `max_fails`/`fail_timeout`; built-in periodic active `health_check` is commercial. Consul can still provide external active checks. | Core active and passive checks for configured upstreams. **Active checks do not run for dynamic upstreams**; DNS discovery should return healthy targets. |
| Retry controls | Service retries/timeouts, with different handling of connection failures and requests already sent. | Rate limiting | OSS Rate Limiting offers local, database-cluster and Redis counters, subject to deployment-mode limits. Important configuration details:

- Traefik Consul Catalog defaults to accepting **passing and warning** health states. Set `strictChecks` to `passing` to match this gateway's `passing=true` behavior. Disable automatic public exposure and allow only public route definitions; do not expose private domain RPCs merely because they register with Consul.
- NGINX upstream `resolve` and SRV `service` support became available in OSS in **1.27.3**. “Dynamic DNS requires Plus” is outdated. DNS refresh still does not discover HTTP route rules or implement the current fixed-URL fallback policy. See the version annotations in the [upstream reference](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#server).
- Do not infer that every distributed rate limiter requires Traefik Hub: its current [OSS RateLimit reference](https://doc.traefik.io/traefik/reference/routing-configuration/http/middlewares/ratelimit/) documents Redis distribution, while the separately named [DistributedRateLimit middleware](https://doc.traefik.io/traefik/reference/routing-configuration/http/middlewares/distributed-ratelimit/) is Hub-only. The broader Hub comparison matrix is less precise about this distinction.

### Commercial products and integration risks

**Kong Enterprise/Konnect** add commercial capabilities and management options; they are not synonyms for the OSS image. Request Callout is explicitly [Enterprise-only](https://developer.konghq.com/plugins/request-callout/). It can call Auth, but the integration must translate Auth denial/errors and verified identity correctly. Native JWT is credential/Consumer-oriented; it does not automatically map application `sub` to this project's `x-user-id`. Do not substitute Kong Consumer identity for user identity. An unlicensed Enterprise deployment is not a dependable free-OSS deployment strategy: current [license-expiration behavior](https://developer.konghq.com/gateway/entities/license/#expiration) restricts configuration changes and restart behavior in some topologies.

**Traefik Hub API Gateway** adds native JWT/OIDC/token-introspection and other commercial middleware. Its [current introduction](https://doc.traefik.io/traefik-hub/api-gateway/intro) documents Docker and other deployment platforms as well as Kubernetes; do not claim it is Kubernetes-only. Separate API-management features and licensing should be assessed if actually needed. OSS ForwardAuth already permits this project's own Auth service to make current-state decisions.

**NGINX Plus** adds native JWT, active health checks and additional runtime-management capabilities. Separate commercial products such as [NGINX One Console](https://docs.nginx.com/nginx-one-console/) provide fleet configuration, monitoring and security-management workflows. Compare these explicitly when API governance or commercial support matters; neither plain OSS nor a Plus proxy installation automatically constitutes a complete API management rollout.

**Caddy** supplies [automatic certificate management and HTTPS redirects](https://caddyserver.com/docs/automatic-https) in core. Docker label discovery, JWT validation and request-rate modules introduce separate extension ownership and build/version compatibility. Its core [forward_auth directive](https://caddyserver.com/docs/caddyfile/directives/forward_auth) must not be confused with similarly named non-standard JSON modules in the module catalog. Configuration can be updated through its [administration API](https://caddyserver.com/docs/api); keep one authoritative configuration workflow.

There is a Kong documentation discrepancy: the [JWT plugin page](https://developer.konghq.com/plugins/jwt/) lists `grpc/grpcs`, while the [global plugin protocol table](https://developer.konghq.com/gateway/entities/plugin/) marks JWT unsupported for those protocols. Verify the exact release/plugin combination before using JWT on a native gRPC route. It does not block the accepted REST gateway design.

### Conditional fit for Tutor Matcher

**Recommendation, not a user decision:** if replacing Express is the objective and the hosted target remains Swarm with Consul, **Traefik Proxy OSS plus an Auth ForwardAuth endpoint is the strongest first candidate**. Its native providers match both deployment sources, and external Auth can enforce current restrictions without paid JWT middleware. Choose one source of public route definitions and test discovery failure/fallback explicitly.

**Kong** becomes attractive when gateway-managed API policies, Consumers and plugin governance are central, provided its Auth adapter and edition/version maintenance are acceptable. **NGINX OSS** fits a team that prefers explicit proxy configuration and Auth subrequests, accepting additional discovery/configuration work. **Caddy** fits when straightforward HTTPS and a small explicit route set dominate, accepting DNS/controller integration and any required community modules. Retaining and improving the current Express gateway is also a valid minimal-change option near the delivery deadline.

For every option, preserve the REST contract, check current Auth state, replace all client-supplied identity headers, deny protected requests when Auth cannot establish permission, keep ownership checks in services, and avoid retrying financial/workflow mutations without their idempotency contract. Test revoked/suspended users, spoofed identity, unhealthy targets, Consul outage, Auth outage and retry duplication before switching traffic. No migration, benchmark, subscription purchase or deployment was performed for this research.

These alternatives were evaluated against the then-current Swarm/Doco-CD delivery. The user later selected Traefik with native Swarm discovery, replacing Consul; the historical Consul comparison below is not a current requirement. ### What is being deployed

At research time, the checkout had six runnable applications (custom Gateway, Auth, Tutor, Booking, Wallet, Notification), root local Compose, PostgreSQL, MongoDB, RabbitMQ and Consul. That snapshot is historical. The target adds the Next.js frontend, Review and Messaging, changes Booking persistence to PostgreSQL, and requires durable outbox and owner-worker processing. Do not assess current readiness from that snapshot. The accepted target has three PostgreSQL databases and four MongoDB databases, with separate ownership even when engines are shared. A database per service does not require a separate cloud database instance per service.

The current Booking process has separate REST and gRPC listeners on 4004 and 50052. The target retains public-facing REST operations and 20 private domain RPCs across five gRPC servers. ### Homelab and Compute Engine

Keep separate local and hosted manifests. Build production images in CI and deploy immutable revisions through Doco-CD, retaining explicit demo-provider configuration. Preserve durable PostgreSQL, MongoDB and RabbitMQ data, with initialization/migrations, placement rules, tested backup restoration, readiness checks and smoke tests. Do not expose database, broker, Consul-management or internal domain ports as public application interfaces. These are repository requirements, not claims that the hosted files or server are ready.

A Compute Engine Linux VM can run Docker Engine and the same one-node Swarm. Provision Docker/startup with a supported startup script or cloud-init rather than relying on the deprecated container-startup-agent mechanism. A single VM still has a single-host application failure boundary. If higher availability is required, design multiple failure domains, Swarm manager quorum, application replicas, database/broker replication and recovery together. Adding app replicas on one machine does not address host failure. [Compute Engine container deployment](https://docs.cloud.google.com/compute/docs/containers/deploying-containers), [Docker manager quorum](https://docs.docker.com/engine/swarm/admin_guide/).

Do not put the all-in-one stack in an ordinary autoscaling managed instance group and assume it becomes a cluster. Persistent data and cluster membership require deliberate handling. Stateful managed instance groups preserve selected state but do not support autoscaling. [Stateful MIGs](https://docs.cloud.google.com/compute/docs/instance-groups/stateful-migs).

### Cloud Run

Deploy frontend/API processes as separate Cloud Run services, continuous RabbitMQ/outbox workers as worker pools where appropriate, and finite migrations as jobs. Worker pools are generally available and support pull workloads including RabbitMQ; set running capacity explicitly, or configure external-metric autoscaling. They do not have the ordinary service's load-balanced URL. [Workload models](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run), [release notes](https://docs.cloud.google.com/run/docs/release-notes).

Cloud Run supports gRPC, but it is not a direct port-for-port replacement for this Compose stack. Each service has a single ingress container/port. Adapt Booking's separate REST/gRPC listeners through one correctly configured ingress listener/proxy or separate deployments. Configure end-to-end HTTP/2/h2c for gRPC. [Runtime contract](https://docs.cloud.google.com/run/docs/container-contract), [HTTP/2 configuration](https://docs.cloud.google.com/run/docs/configuring/http2).

Replace the Swarm per-instance discovery model with configured service URLs and platform routing if this alternative is selected. That would amend the accepted Consul design. Give internal callers appropriate service identities and invocation permissions; Google IAM authentication is separate from end-user authentication. A Google ID token in X-Serverless-Authorization can coexist with the application's own Authorization header. [Service authentication](https://docs.cloud.google.com/run/docs/authenticating/service-to-service).

Externalize durable state. Container filesystems and ephemeral disks do not replace PostgreSQL/MongoDB/RabbitMQ persistent volumes. Request-based HTTP service billing does not provide CPU for an idle background consumer. Instance-based billing and minimum instances can support background work, but instances can still restart or terminate. Dedicated workers need reconnection, acknowledgements, graceful shutdown and safe retries. [Runtime contract](https://docs.cloud.google.com/run/docs/container-contract), [billing settings](https://docs.cloud.google.com/run/docs/configuring/billing-settings), [minimum instances](https://docs.cloud.google.com/run/docs/configuring/min-instances).

Cloud Run already handles public HTTPS at the platform entry. Do not add a self-hosted proxy solely to obtain TLS. Keep a gateway only for needed routing, authentication and policy. Avoid assuming that Kong/Traefik/Caddy or NGINX automatically obtains IAM tokens for each internal Cloud Run upstream; that integration must be designed and verified.

### GKE

Use Deployments and Services for frontend/API processes and long-running consumers, Jobs for finite migrations, and explicit probes/resource requests/scaling policies. Prefer externally managed databases/broker when reducing operations is the objective. StatefulSets and persistent volumes can host stateful dependencies, but do not make their backup, replication and upgrades Google's responsibility. [Stateful applications](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/stateful-apps).

Autopilot is the starting candidate unless there is a concrete need for Standard's node-level control. Autopilot reduces node administration but still requires Kubernetes workload design and cost/resource configuration. The native GKE Gateway controller provisions Google Cloud load balancing; that entry layer is separate from application-specific authentication and API policy. [GKE modes](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/choose-cluster-mode), [GKE Gateway API](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/gateway-api).

### Complete build and release choices

A Cloud Build trigger starts builds on configured repository events. Cloud Build runs checks and image builds. Artifact Registry stores images. Cloud Deploy controls releases, promotion and verification. These are separate responsibilities, not four services that every option must use. Existing GitHub Actions can remain the build system even when images and runtimes are on Google Cloud. [Build triggers](https://docs.cloud.google.com/build/docs/automating-builds/create-manage-triggers), [Cloud Deploy CI integration](https://docs.cloud.google.com/deploy/docs/integrating-ci).

| Runtime | Recommended minimal chain | Optional addition |
| --- | --- | --- |
| Homelab Swarm | GitHub Actions checks/builds → registry images by digest → reviewed hosted manifest revision → Doco-CD → migrations/readiness/smoke checks | Artifact Registry can be the registry if deliberately selected; native Google build services are not required |
| Compute Engine + Swarm | Same chain and Doco-CD, targeting the VM-hosted stack | Cloud Build can replace GitHub Actions; keep one build authority |
| Cloud Run | Repository event → Cloud Build trigger → checks/build → Artifact Registry → explicit deployment steps for services/workers → verification | Cloud Deploy when staged release/promotion/canary controls justify it |
| GKE | Repository event → Cloud Build trigger → checks/build → Artifact Registry → Cloud Deploy release → staged Kubernetes rollout/verification | Existing GitHub Actions can build and create the Cloud Deploy release instead |

A pushed image does not automatically start Cloud Deploy; CI must explicitly create a release or an event workflow must be configured. Cloud Deploy natively supports GKE and Cloud Run services, jobs and worker pools. For Cloud Run, one target deploys one service/job/pool, so plan per-component pipelines/targets and coordinated release ordering. Jobs do not support canary deployments. Swarm/Compute Engine would require a custom Cloud Deploy target implementation; retaining Doco-CD is the simpler option for this architecture. [Cloud Deploy CI integration](https://docs.cloud.google.com/deploy/docs/integrating-ci), [Cloud Run target limitations](https://docs.cloud.google.com/deploy/docs/run-targets), [custom targets](https://docs.cloud.google.com/deploy/docs/deploy-to-custom-targets), [direct build-to-Run](https://docs.cloud.google.com/build/docs/deploying-builds/deploy-cloud-run).

In every chain, build and verify images before changing desired deployment revisions. Keep mutable latest tags out of release identity. Configure runtime registry access, least-privilege deployment identities, private dependency connectivity, release verification and a data-compatible rollback procedure. Introducing Cloud Build or Secret Manager in place of the accepted GitHub Actions/SOPS approach requires an explicit architecture decision; this comparison does not make that change.

### Cost and decision

No reliable monthly total can be quoted without region, machine/resource sizes, traffic, uptime, minimum instances, managed-service tiers and existing homelab capacity. Compare the complete system:

- Homelab: incremental electricity, storage/backups and hardware replacement, plus operator time and connectivity limits.
- Compute Engine: VM runtime, persistent disks, snapshots/backups, external IP where used and networking.
- Cloud Run: request or instance usage, minimum/warm instances, continuous workers, external database/broker baseline costs and networking.
- GKE: cluster management and workload/node resources, persistent storage, load balancers and external dependencies.
- All cloud choices: builds, image storage, logs/metrics, backups and any applicable NAT, cross-zone/region or internet transfer.

Cloud Run can reduce idle HTTP compute cost without scaling external databases and RabbitMQ to zero. GKE management-fee credits, where applicable, do not make its workload resources free. Reusing one physical database engine with isolated owned databases can reduce the small-demo footprint. Price the same availability and backup design in each option. [Cloud Run pricing](https://cloud.google.com/run/pricing), [GKE pricing](https://cloud.google.com/kubernetes-engine/pricing), [Google Cloud calculator](https://cloud.google.com/products/calculator).

Recommendation, not adoption: retain homelab Swarm/Doco-CD for the current delivery. If the goal is moving the existing design to Google with the least application change, evaluate Compute Engine plus the same Swarm stack. If the goal is fewer application-platform operations and the team accepts discovery/listener/worker adaptations and external data dependencies, evaluate Cloud Run. Choose GKE when Kubernetes capabilities or learning are themselves goals; begin with Autopilot unless a specific constraint calls for Standard.

## Verification and open questions

This is source-based research, not a deployment test or benchmark. No cloud resources, server configuration, accounts, commits or pushes were changed. The local code and accepted design differ; a documented target does not prove implemented behavior.

Before selecting a migration, resolve region/budget, available homelab capacity and ingress, required uptime, managed database/broker tiers, expected traffic, continuous-worker counts, data migration/restore requirements and whether the accepted course architecture can be amended. Any gateway replacement must be verified for public/private route boundaries, fresh Auth account-state checks, client identity-header replacement, Consul outage behavior if retained, safe mutation retries, gRPC behavior, and durable worker recovery.
